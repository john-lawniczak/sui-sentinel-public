# R1 operations release-candidate review — 2026-11-02

The cached-monitoring implementation is substantially stronger, but **R1 is not
production-qualified**. Local implementation, full-market measurements, failure
checks and recovery evidence are complete as described below. Production was not
provisioned or deployed. The seven-day soak, hosted recovery, selected-provider
full census and rendered/operator UX checks remain open.

the commit containing this review. Local images deliberately use build identity
`4f72f03-candidate`; production startup rejects that value. The security workflow
builds from the actual full commit hash and retains image identity, SBOM and scans.

`sha256:159a3506c6cc1e08e71e1658d73f222216ccda3c38fcd5576eb84a4bc3131534`.
The complete successful census used the earlier candidate image; the final image

## Verification and recovery

- **123 Rust tests passed**, with real PostgreSQL, including HTTP acceptance
  followed by worker cancellation before acknowledgment, stable replay identity,
  ordered/manual retry rejection, debounce/recovery/reminder persistence,
  acknowledgment audit, historical outbox evidence retention, endpoint protection,
  QuickNode header behavior and descendant cleanup after timeout/cancellation.
- Formatting, Clippy with warnings denied, file-size enforcement and generated
  dashboard consistency passed. Two Python sampler tests passed, including
  missing/late samples and duplicate-slot rejection.
- Running Grafana validated **41 panel queries**, all-market/single-market
  filters, persisted layout/configuration and totals against the full report.
  Prometheus validated its configuration and **five alert rules**. These are
  query/provisioning checks, not rendered visual or human-operator tests.
- The final non-root Linux container served authenticated status, rejected public
  status with 401 and kept liveness public. With the provider deliberately
  unavailable, it recorded four failed attempts/three retries, delivered
  Discord-format operational messages to the local test receiver, drained its
  outbox and retained the still-fresh last-good report. Observer/database health
  stayed true; this distinguishes a failed capture from unavailable cached data.
- Seven transactional database permission checks passed: monitor can read retained
  audit evidence, reader/delivery cannot mutate incidents, monitor cannot create
  tables, and operator cannot change severity or delete audit history.
- Actual 64 KiB tmpfs exhaustion caused `ENOSPC`; capture failed and the existing
  publication pointer survived. The test does not simulate every disk failure phase.
- R1 operations backup restored one incident and two outbox entries with matching
  deterministic content hashes. Non-chain notifications were included, rather
  than relying only on replayable blockchain state.
- Full projection backup/restore of a **3,560,956,431-byte database** took
  **7.153 s backup + 11.030 s restore = 18.183 s** locally. Restored checkpoint
  **340925943**, all **296,151** object versions/bodies, **150,164** evaluations
  and **1,030,000** dependency rows matched deterministic source hashes.
  This exceeds the amount of state needed for cached-only R1, but uses local
  Docker storage; it does not establish remote transfer or hosted PITR performance.

Tokio was upgraded to 1.54.1 after the scan identified the interval race described
in [the Tokio advisory](https://github.com/tokio-rs/tokio/security/advisories/GHSA-5wjr-9356-4wc8).
The runtime moved from a general-purpose slim image to pinned distroless Debian
with a small static BusyBox toolset required by process supervision and disk checks.
Final Trivy 0.76.1 lockfile/image scans reported **zero HIGH/CRITICAL findings**.
The Rust lockfile scan is necessary because the image scanner did not identify
embedded Rust dependencies. Manually copied BusyBox and application code are not
proved vulnerability-free by the OS package scan. This is not a security audit.

## Soak result and limitations

The independent sampler recorded **40/40 available** slots during a 600-second
smoke run, with **30/40 ready** slots. Startup/capture time remained in the
denominator. The verdict was correctly **INCOMPLETE**, with an unpinned candidate
revision; this is neither a passed seven-day test nor a 99.9% reliability claim.
That smoke run used the earlier candidate before the final `observer_ok` readiness
check; the final sampler additionally requires successful observation.

Rendered browser checks could not run: the installed browser runtime failed at
initialization with `Cannot redefine property: process`. No screenshots, mobile
layout, keyboard-navigation or human operator timings are claimed. The browser
skill's permitted runtime was used; API checks did not substitute for visual QA.

Hosted Fly credentials/volume/DB, Discord channel acceptance, independent outage
paging, PITR, upgrade rollback and the seven-day run remain pending. Fly CLI was
not installed; local TOML/security validation passed, not account-side validation.
No production changes were made. BlockVision gRPC remains the selected live source,
but live catch-up throughput, real mutation coverage and fresh financial math
remain outside the qualified R1 capability.

Follow the [release runbook](../operations-release.md) and remaining tasks in
[release gates](../readiness.md). Maintain these distinctions when assigning readiness
scores; the release cannot be declared production ready solely from these tests.
